# 从游戏资源到家具3D：Mesh、GLB与网页显示

## 文件类型与用途

| 文件                | 内容                                                   | 处理方式                                                                |
| ------------------- | ------------------------------------------------------ | ----------------------------------------------------------------------- |
| `.blueprintx`       | 家具资源编号、样式、实例、挂接关系和变换               | 导出、校验与组件预览；文件本身不包含家具网格或贴图                      |
| `.Mesh` / `.Prefab` | 游戏表现资源：几何，或模型/灯光/特效的装配描述         | 离线读取指定资源；已支持的Mesh布局可转成几何GLB                         |
| `.glb`              | glTF 2.0的二进制容器，可装几何、材质、纹理、层级和动画 | 几何工具输出中性模型，材质工具另写UV、贴图与染色方案；网页读取自包含GLB |

**GLB是本工程工具从本机游戏Mesh的实际顶点和三角索引生成的。** 输出保留源网格的几何拓扑。38件样本保留输入SHA256，并通过独立GLB格式校验。几何工具输出中性检查模型；材质工具输出贴图、材质分区与染色方案，完整流程见[家具贴图与材质](21-furniture-materials.md)。完整Prefab、场景灯光和动画不在此范围内。

拼布组件预览是另一条路径：读取蓝图节点，以已核对的实体尺寸生成薄盒并实例化显示。该路径使用尺寸资料，不需要把原游戏模型放入网页。

## 1. 家具资源定位

```text
家具目录中的 type + furnitureId
    ├─ 分类、名字、库存身份、缩放范围
    └─ nRepresentID + nBrushModeCnt
         ├─ ID_Model：模型 / Prefab / 动画 / 特效等
         ├─ ID_Brush：普通笔刷
         └─ ID_CustomBrush：植被或地表材料
```

家具ID、表现资源ID、蓝图实例ID是不同的编号。不同资源表可以复用同一个数字，必须连同表名理解。`build_furniture_index.py`按类型/笔刷模式分派，保留反向家具身份；同资源对应多个家具目录记录时，不据此合并库存。

五张资源表的相对路径见 `tools/furniture-resource-paths.txt`。生成命令：

```sh
python tools/build_furniture_index.py --assets ./client-assets --output ./docs
```

索引保留源文件字节数、SHA256、原始空值和测试标记。`resourceFound=true`只代表能定位资源条目，`identityMatched=true`才表示该条资源的反向家具类型/ID也一致。详细数量见 `furniture-coverage.json`。

### 直接Mesh与Prefab的区别

天青照影方椅的表现资源19315直接指向 `chair1_1_1067_HD.Mesh`；香薰蜡烛20831直接指向 `Ornament4_2_1011_HD.Mesh`。

西苑亭灯20938指向 `Light1_1_1266_HD_P_L.prefab`。其中 `actorModel` 再引用 `wj_街灯001_hd.mesh`，另有灯光相关成员。仅转换actorModel得到灯的网格，尚未应用完整Prefab的内建矩阵、发光或其他成员。因此样本标注“网格”，模型XYZ尺寸也不直接等同最终摆放家具尺寸。

## 2. 按清单读取本机资源

`tools/read_client_assets.cpp`使用已安装游戏的文件系统导出接口，按给定路径清单读取Pakv4内的本地文件。它不启动游戏，不注入游戏进程，不修改资源包，也不枚举并导出整个资源库。

开发者需要Windows x64编译器和自己的完整本机资源。接口与资源快照相关，不能假定任意版本的DLL和Pak能混用。路径清单使用GBK编码，每行一条资源内部相对路径；中文路径必须能往返编码。

```text
read_client_assets.exe <bin64目录> <Pakv4目录> <GBK路径清单> <输出目录>
```

实现顺序：加载本机Engine_Lua5X64与KGPK4_FileSystemX64；取得初始化、挂载和打开文件的导出入口；挂载本地Trunk.dir；逐条校验路径并读取。拒绝绝对路径、盘符、空段、`.`和`..`；已有输出保留，不覆盖。索引有记录但本地数据缺失时，报告具体缺失项并停止对应转换。

源码仓库提供工具、数值元数据、证据索引，以及部分经转换压缩的 GLB 和内嵌贴图。

## 3. 已支持Mesh的字节布局

`tools/inspect_mesh.py`是明确收窄范围的几何读取器。所有偏移从文件开头计，整数/浮点为小端。读取器支持未压缩布局2及已核对的静态压缩子集`0xe4000000`、`0xe0000000`。下表描述布局2，压缩流按独立规则解码。

| 文件偏移   | 类型  | 读取含义/条件                                  |
| ---------- | ----- | ---------------------------------------------- |
| 0x54       | 4字节 | 标记 `HSEM`                                    |
| 0x58       | u32   | 声明长度，必须等于文件字节数                   |
| 0x5c       | u32   | 未压缩布局标记2；压缩子集见下文                |
| 0x8c       | u32   | 当前支持值1                                    |
| 0x90       | u32   | 顶点数                                         |
| 0x94       | u32   | 三角形数，索引数量为其3倍                      |
| 0x98       | u32   | 材质槽数量；材质工具逐Group验证Subset数量      |
| 0x9c       | u32   | POSITION流起点，顶点数×float3                  |
| 0xa0       | u32   | NORMAL流起点，顶点数×float3                    |
| 0xa8       | u32   | UVW流起点，顶点数×float3；材质工具取前两列为UV |
| 0xac、0xb0 | u32×2 | 附加流字段；非0即拒绝当前转换                  |
| 0xb4       | u32   | 索引流起点，三角形数×3×u32                     |
| 0xb8       | u32   | 材质索引流起点，每三角形一个u16槽号            |

约束：输入276字节至64MiB；顶点1～200,000；三角形1～400,000；所有流在文件内且不重叠；浮点有限；索引小于顶点数；被引用法线长度在0.5～1.5以内。报告中的位置包围盒涵盖源位置流；GLB只保留实际被索引使用的顶点，因此GLB包围盒可能更小。

未支持布局保留原文件及诊断记录。压缩流与附加流使用各自的解码规则。地下室使用的`0xe4000000`位置、法线和UV子集已有专用核对与转换；`0xe0000000`已通过夏木听风榻核对相同的位置、法线和UV解码。其`0xa4`顶点色与`0xd0`Byte4切线分别做范围和重叠校验；预览切线按几何重建，顶点色尚未参与材质。附加UV和其他变体仍须单独核对。

## 4. 纯几何 GLB 生成流程

调用：

```sh
python tools/inspect_mesh.py input.Mesh --output geometry-report.json --glb furniture.glb
# 需要其他单位约定时显式指定；默认100单位/米：
python tools/inspect_mesh.py input.Mesh --output geometry-report.json --glb furniture.glb --units-per-meter 100
```

算法顺序：

1. 完整验证Mesh并计算输入SHA256。
2. 收集索引实际引用的顶点，按原编号排序，建立旧编号到新编号映射。
3. 位置除以units-per-meter；不交换坐标轴、不额外翻转索引。转换保留资源坐标，Prefab装配与游戏实景朝向尚需另外核对。
4. 法线归一化，不把位置缩放误乘到法线上。
5. 按映射重写索引，保留三角形顺序与拓扑；移除未被索引引用的顶点。
6. 位置、法线和索引分别编码为连续二进制流。
7. 用实际编码后的float32位置计算accessor的min/max，避免JSON边界与二进制值因舍入不一致。
8. 生成一套中性PBR材质和一个三角形primitive，再打包JSON与BIN。

### 输出结构

```text
GLB头：magic=0x46546c67，version=2，完整length
JSON chunk：UTF-8描述，空格填充到4字节边界
BIN chunk：位置float32 → 法线float32 → 索引uint32
```

JSON中：

- `scene/scenes/nodes`：一棵只含几何检查节点的场景树。
- `meshes[0].primitives[0]`：POSITION=0、NORMAL=1、indices=2、mode=4（三角形）。
- `bufferViews`：三段流的字节偏移和长度，顶点target=34962，索引target=34963。
- `accessors`：位置与法线为5126/VEC3，索引为5125/SCALAR；count以元素数量计算，不是字节数。
- `materials`：中性灰蓝 `[0.72,0.74,0.78,1]`，metallic=0、roughness=1、doubleSided=true。它是检查材质，**不是从游戏还原的原色或粗糙度**。
- `extras`：几何输出范围、源文件SHA256、使用的单位换算。

纯几何转换路径不输出 `TEXCOORD_0`、原材质子集、贴图、骨骼、动画、LOD或游戏专用效果。读取到UVW流不能等同已经正确映射了贴图；单primitive输出不包含原始多材质分区。

标准格式参考：[glTF 2.0规范](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html)。

## 5. 几何来源与输出验证

最小证据链包括：输入Mesh哈希、受支持布局、流范围、原/使用顶点数、三角形数、GLB哈希、单位策略、独立格式校验和实际可见结果。

`model-geometry-check.json`记录216个样本的汇总和37份几何输出。37份输出经[Khronos glTF Validator](https://github.com/KhronosGroup/glTF-Validator)校验，错误和警告均为0。几何工具的合成测试还检查索引重映射、单位换算、截断、未知标记、NaN与流重叠拒绝。

格式校验不能证明游戏原材质正确、所有资源都支持、模型方向已与游戏一致或原家具能保存。预制体内部成员、挂面和完整效果需要另做游戏侧比对。

## 6. 网页加载与显示

入口在 `furniture-panel.ts`；文件约束在 `model-file.ts`；渲染在 `furniture3d.ts`。Three.js与GLTFLoader按需加载，OrbitControls控制相机。

GLB必须自包含：不接受JSON里的外部uri，图片应通过BIN中的bufferView内嵌。浏览器额外通过LoadingManager拒绝非blob资源。文件上限50MiB，JSON块上限8MiB，节点上限3,000，访问器元素总数上限8,000,000，显示三角形上限1,000,000；节点循环和过深层级会拒绝。需要额外解码扩展的模型先转换为普通GLB。

加载成功后按模型世界包围盒计算中心、相机距离与尺寸。尺寸标题写“模型XYZ”，单位按GLB米制约定；上传文件若本身用了错误单位，查看器不会自动猜测修正。

查看器提供正面、侧面、俯视、重置视角和结构线。演示照明由中性棚光环境、半球光和方向光组成，地面网格只是观察参考。它不播放动画、不模拟灯笼火焰，也不读取游戏天气。切换模型会释放旧geometry/material/texture；切换工作区或隐藏页面暂停绘制，页面退出释放WebGL上下文。没有持续自动旋转，静止时不耗循环渲染。

## 7. 内置样本与项目构建

38 份家具样本随项目置于 `assets/models/furniture/`。`scripts/prepare-furniture.mjs`检查清单与文件名、GLB头和长度，复制指定模型并记录SHA256。输入清单和GLB放在同一目录：

```json
[{ "file": "chair.glb", "name": "椅子", "category": "桌椅", "note": "单件预览示例。" }]
```

```sh
node scripts/prepare-furniture.mjs preview-manifest.json
pnpm dev
```

开发服务、静态网页和桌面程序使用同一套内置样本库，按需读取 GLB；单文件离线 HTML 使用手动模型入口。源码 ZIP 包含 `assets/models/`，排除临时 `artifacts/`。网页压缩、资源绑定与新增家具步骤见[内置模型库](24-model-library.md)。游戏美术资源的权属独立于工具代码的 MIT-0 许可。

## 8. 布置数据与蓝图导出

在线布置已对36件绑定家具实现选取、变换、复制删除、撤销重做和真实蓝图导出。工程同时保存“游戏对象数据”和“显示模型”关联：GLB只承担显示，游戏资源和SRT来自工程数据。完整数据结构和写入过程见[在线布置与导出](20-scene-editor.md)。

| 数据                   | 保存要求                                           |
| ---------------------- | -------------------------------------------------- |
| 资源表名、表现资源ID   | 确定游戏实际加载哪个资源；同数字可能属于不同资源表 |
| 家具类型、家具ID       | 库存核算与资源身份，不等同GLB文件名                |
| Detail、flags、builtin | 样式、已确认状态和内建成员关系                     |
| 唯一实例ID             | 编码、父子关系及编辑操作对应                       |
| 父节点、挂面/槽索引    | 家具挂接关系；不能只存最终世界坐标                 |
| 世界位置、四元数、缩放 | 工程保存世界变换；导出时换算到父对象或挂面         |
| 缩放维数和资源限制     | 决定字段长度与合法值，不可凭GLB包围盒猜            |
| 未解释的原始块         | 对不支持部分保持只读和原样保存，不能静默删除       |

编辑器以游戏对象数据为主数据，Three.js场景是它的显示映射。拖拽产生编辑空间的变换，按坐标轴约定、父节点、挂面以及该节点的缩放约定转回文件局部值；渲染实例矩阵需经坐标与层级转换后才能序列化。一次拖动提交为一个撤销事务，取消或撤销还原整份数据修改。

导出顺序为：对象/资源校验 → 分配唯一实例编号 → 编码节点及有界子树 → 计算摘要 → 重新解析完整文件 → 比较ID、数量、父子结构、变换与未知块 → 输出 `.blueprintx`。最后还要在游戏内确认导入、摆放、保存和重载。

仅有任意GLB而没有对应游戏资源，不能把它当新家具导入游戏。即便GLB外观像已有家具，也需要明确的资源映射，不能按相似度猜编号。Prefab样本还必须恢复内建节点和挂面定义；只拿其中一个Mesh会遗漏原家具装配信息。

## 9. 完整家具支持的扩展要求

| 层     | 已能核对                                        | 后续实现所需证据                                   |
| ------ | ----------------------------------------------- | -------------------------------------------------- |
| Mesh   | 未压缩布局2及地下室压缩子集                     | 高位格式、更多流布局、子集、LOD、骨骼蒙皮          |
| Prefab | actorModel路径及部分内部变换                    | 全节点矩阵、成员启用状态、Detail与挂面             |
| 材质   | 38件的分区、UV、基础色/法线/MRE、透明、染色方案 | 动态水面、复杂混合、视角特效及更多着色器           |
| 纹理   | DDS/CRN和连续HDD高清层、通道与色彩空间、内嵌PNG | 更多压缩格式、流式加载和大规模纹理预算             |
| 灯光   | 184/344兼容映射和已命名字段                     | IES、阴影、闪烁、扩展参数与网页光照近似方案        |
| 场景   | 局部组件、地下室整屋结构及空绘制块              | 地表/植被渲染、环境探针、天气与全局编辑            |

各层实现应分别提供最小样例、可复现验证和适用范围。视觉相似度不作为完整链路验收依据。
