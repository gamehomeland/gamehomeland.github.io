# 蓝图导入与家园限制

蓝图保存家具和摆放关系。文件能读取、组件能放进编辑器、家园能正式保存，是三个不同的检查阶段。

## 限制概览

| 限制           | 实际含义                                           | 制作前检查                                 |
| -------------- | -------------------------------------------------- | ------------------------------------------ |
| 可用家具       | 拼布和基座都要核算库存；已摆放家具会占用可用数量   | 按下载包的清单准备，导入后查看游戏缺失清单 |
| 等级与分类容量 | 不同家具分类按家园等级读取各自上限                 | 核对当前分类的剩余容量，不能只看总件数     |
| 单种家具上限   | 同一家具在地块内还可能有独立数量限制               | 大面积同色图案也要留意单种拼布的剩余量     |
| 存储与交互占用 | 保存时另有家具存储和交互对象占用检查               | 关注建造界面占用提示，家具件数不是唯一指标 |
| 地块与尺寸     | 整屋蓝图与局部组件的导入流程不同；实际空地影响摆放 | 按局部或整屋类型选择入口，并保存原有布置   |
| 缩放与旋转     | 不同家具具有不同的合法范围和能力                   | 使用资源允许的缩放范围                     |
| 操作状态       | 正在导入、移动、拆除或查询消耗时，部分操作会被阻止 | 先确认或取消当前操作，再导入或保存         |

工具无法读取玩家库存、等级和已有场景。**生成成功表示文件与布局检查通过；能否保存到家园，仍需游戏核算。**

## 1. 分类容量、单种数量与库存检查

增加家具的流程按一级分类、二级分类和当前等级调用 `GetLevelFurnitureConfig(...)`，把返回的 `LimCount` 与“已有数量＋新增数量”比较。错误列表还会逐级查询容量，提示所需等级。

普通家具另读取 `GetFurnitureConfig(id).nMaxAmountPerLand`，核对同一家具在当前地块的数量。可用库存通过 `BuildGetFurnitureCanUse(...)` 查询，家具等级要求通过 `nLevelLimit` 检查。满足其中一项不表示另外几项也通过。

特定 `PENDANT` 类型在所核对的增加流程中使用单件上限。这不能扩展为“所有挂墙家具只能摆一件”，也不适用于普通拼布。

设计模式与实地建造模式的库存处理不同；已观察到分类和单种限制的检查先于设计模式提前返回，不能把设计模式理解为无限容量。

## 2. 存储占用有独立阈值

保存检查、界面显示和底层比较采用以下计数阈值：

| 项目                          | 所核对的超限条件        | 累计方式                       |
| ----------------------------- | ----------------------- | ------------------------------ |
| 家具存储占用 `SDSize`         | 当前累计值 **≥ 7,936**  | 按型号对应的存储成本乘数量累计 |
| 交互对象占用 `LandObjectSize` | 当前累计值 **≥ 12,288** | 按型号对应的对象成本乘数量累计 |

阈值按各自计数器的占用单位计量，**不按家具件数计量**。底层增加函数分别调用两种成本计算，再乘新增数量；不能用本工具导出的总件数直接换算占用百分比。

`HLBOp_Check.CheckSave` 和 `CheckAutoSave` 调用两项超限检查；`HLBView_Saveusage.Update` 使用“当前值、上限”显示百分比。达到阈值已经会被判超限，不能按“等于上限还可保存”处理。

## 3. 保存数据与传输数据的大小限制

`GetSDKFileLimit` 对游戏生成的保存数据查询两组“大小、阈值”：

| 项目                         | 所核对的规则                                                   |
| ---------------------------- | -------------------------------------------------------------- |
| 普通分支的原始数据           | 阈值 **3,145,728 字节（3 MiB）**                               |
| `PRIVATE` 条件分支的原始数据 | 阈值 **6,291,456 字节（6 MiB）**                               |
| 上传阶段的原始数据检查       | 达到或超过所选阈值即拒绝                                       |
| 压缩后传输占用               | 压缩并编码后的长度加 1,000，与运行时配置的阈值比较；超过即拒绝 |

界面在 `BUILD_MODE.PRIVATE` 中传入私人地块条件，设计模式根据设计目标的类型决定；实际上传分支由游戏根据目标地块判定。压缩阈值从运行时状态读取，不能从蓝图文件推导固定数值。

**阈值适用于游戏保存和上传数据。ZIP或局部`.blueprintx`文件大小不能直接用于判断该条件。**局部组件与整屋保存采用不同的文件和流程。

## 4. 地块、整屋与局部组件

整屋导入准备分支检查文件标记、版本，并比较蓝图记录的两个场景尺寸与当前场景尺寸。局部组件走相应的组件流程。整屋尺寸比较中的数值容差不能解释成局部拼画的最大宽度。

图片拼布及未合并原整屋的普通家具布置生成 `global=0` 局部组件；含地下室或合并原整屋时生成 `global=1` 整屋蓝图。新建整屋的地表/植被绘制块为空；合并导出保留原文件对应数据块。工具允许生成 200 米地面图案，不代表每个地块都有这么大的可用面积。

实际摆放还受场景、位置和家具自身条件影响。地块与模式的尺寸要求分别适用，不存在由本文资料推导出的全游戏统一宽高边界。

设计预设表包含32×40、40×56、56×72、72×100、56×112、104×112、212×216七组长宽，分别对应1280、2240、4032、7200、6272、11648、45792平。私宅完整范围为212×216米，含7个分区；社区资料包含5张地图108块土地的四角坐标。面积、分区图与坐标规则见[地块规格与布局](22-land-layouts.md)。设计预设不等于每位玩家当前拥有的可用面积。

## 5. 家具尺寸、地下室与合法缩放

地下室通过级联笔刷和专用地形洞口模型实现。普通家具负高度、地形开口与地下通行规则分别核对；地块的水平边界不定义统一地下深度。资源与实现范围见[地下室与地形洞口](23-basement-and-terrain.md)。

当前数值资料的 144 个拼布规格逐件核对了等比缩放范围 **0.25～2 倍**：

| 家具规格 | 合法实体边长 |
| -------- | ------------ |
| 2 米拼布 | 0.5～4 米    |
| 4 米拼布 | 1～8 米      |

微缩布局让每块家具只露出较小的可见部分，实体本身仍在合法范围内。它不修改最小缩放，也不保证侧面观看与正面一样。

其他家具可能有不同范围；非等比缩放需要资源明确允许。高度面板按各家具的 `szHeightLimit` 设置范围；字段为空不能推断为无限高度。多个家具同时缩放时，面板会综合各自可用范围。

## 6. 挂接与文件结构

挂面、挂点类型和索引由相应家具资源定义。父子关系不能形成祖先循环；预制体内建成员与玩家新摆家具要分别核算。

直接子节点计数是 `uint16`，可表达 0～65,535；这是文件字段宽度，**不是家园容量或挂接数量承诺**。导出器使用的分组大小同样不能当作游戏上限。

加载流程会检查蓝图版本、长度、节点内容和尾部摘要，再检查资源及对象能否建立。不同整屋/局部入口不能靠改扩展名互换。文件被截断、资源不存在或修改字节后没更新摘要，都需要修正生成流程。

## 7. 临时状态与正式保存

导入后会进入加载或移动预览状态，需要确认或取消。移动、笔刷、多选、拆除、消耗查询和部分快捷键状态，会阻止不适合同时执行的操作。

缺少家具、超量或等级不足会进入游戏错误清单。导出文件不消耗库存，也不代表已经应用到家园；应完成摆放、保存，再重新进入核对。

## 8. 本工具的边界

以下属于工程的输入与计算预算，不是游戏统一限制：

| 项目         | 当前范围                                                                        | 代码入口                                 |
| ------------ | ------------------------------------------------------------------------------- | ---------------------------------------- |
| 输入文件     | 50 MiB；PNG、JPG、静态 WebP、GIF 首帧                                           | `image-limits.ts`、`upload.ts`、`gif.ts` |
| 图片像素     | 最多 8,000,000 像素                                                             | `image.ts`                               |
| 成品长边     | 墙面 1～96 米；地面 1～200 米                                                   | `validateOptions`                        |
| 家具预算     | 默认自动规划，可自定义含基座总件数；工具保护值由节点/字节预算求得，不是玩家容量 | `budget.ts`、`validateOptions`           |
| 网格长边     | 单轴最多512格，节点、家具与实体尺寸继续限制二维总量                             | `prepareImage`                           |
| 文件解析预算 | 32,000,000 字节、250,000 节点、128 层递归                                       | `codec.ts`                               |
| 蓝图能力     | 拼布和绑定家具局部组件；含地下室的整屋蓝图及地板挂接；不支持任意场景写回        | `codec.ts`、`layout.ts`、`editor.ts`     |

输入图片大小、ZIP 大小、蓝图节点数、家具件数与游戏存储占用应分别理解。

## 核查入口与验证范围

规则索引、数值、模块哈希和函数位置见源码中的 `docs/game-limits-evidence.json`。关键入口包括 `HLBOp_Check.CheckAdd/CheckSave`、`HLBView_ErrorItemList.UpdateErrorItemOverflow`、`HLBView_Saveusage.Update/UpdateLimitationProgress`、缩放与高度面板，以及 `KRLHomelandBuilder::StartLoadBlueprint/LoadBlueprint`。

上述为所核对实现中的规则，游戏更新后需重新确认。全服统一的家具总件数、完整地形与垂直边界、服务端检查和所有家具类型的挂接极限仍缺少充分证据。本文不以孤立常量补齐未知项，实际容量以当前游戏地块及界面为准。
